Explaining a system in prose…

So the booking flow starts in the guest web app, which goes through the API gateway to the booking service, except for availability, which the inventory service answers from the Redis cache, unless the cache is cold, in which case it reads the bookings database directly, and when a booking is confirmed the booking service calls the pricing service for a final quote, then the payment provider, then writes the reservation and an outbox row in one transaction, and the outbox relay publishes an event on NATS that the inventory service consumes to update availability, which it also syncs to the channel manager, and the front desk app sees the new booking through the same gateway, although it talks to a different set of handlers, and refunds go the other way round, roughly, with a few exceptions…

How it works

Runs on your machine · no network calls · nothing published

Can you explain how this service works?
So the service sits behind the API gateway and takes requests over HTTP, except for the bulk path, which arrives on a queue, and both paths end up in the same handler after validation, which checks the payload against the schema registry, unless the client sends a version header older than v3, in which case a compatibility layer rewrites the payload first, and then the handler loads the account from the primary store, or from the cache if it was touched in the last two minutes, which is usually the case for the busy accounts and almost never for the rest. The account carries the plan and the feature flags, and the flags decide which of the three pipelines the request goes through, the fast one for small payloads, the batched one for anything over a megabyte, and the legacy one for accounts that have not migrated yet, and each pipeline has its own worker pool with its own concurrency limit, which is read from configuration at start-up and can be changed at runtime through the admin endpoint, although nobody does that because the change is not persisted and is lost on the next deploy. Writes go to the primary store inside a transaction together with an outbox row, and a relay process publishes the outbox rows to the event bus, where the downstream consumers pick them up, the search indexer, the reporting job, the audit log and the webhook dispatcher, which calls customer endpoints with retries and backoff and gives up after six attempts, at which point the event is parked in a table that an operator has to look at by hand, which happens more often than it should. Reads are served from a replica, except right after a write by the same client, when a short-lived flag in the session makes the next few reads go to the primary so the client sees its own change, and the flag expires after five seconds or after three reads, whichever comes first, and this is also why some of the integration tests are flaky, because they read exactly at the boundary and get either the old or the new value depending on timing. Authentication is a token checked at the gateway, but authorization happens inside the service per resource, through a policy module that evaluates rules from the policy store, which is cached per account for one minute, so a permission change can take up to a minute to apply, except for revocations, which are pushed through the event bus and applied immediately, and the two paths occasionally disagree for a few seconds, which is documented as a known limitation. Rate limiting is done twice, once at the gateway per API key and once in the service per account, with different windows, and the service one is the one that actually bites under load because it is shared with the bulk path, so a large import can starve the interactive requests of the same account, which is why there is a reserved quota for interactive traffic, configured as a percentage, which was set to twenty once and never revisited. Observability-wise every request gets a correlation id at the gateway that flows through the handler, the pipelines, the outbox and the consumers, so a single request can be followed end to end in the tracing tool, as long as sampling kept it, and the sampling rate is ten percent in production, so a rare slow path may not be visible until it is common, and the logs are structured but each component names the same field differently, which makes joining them take a little care. And finally deployment: the service ships as one container with a sidecar for the relay, rolled out as a canary first, promoted when the error budget allows it, with migrations run ahead of the rollout by a separate job that has to be backwards compatible with the previous version because both run at the same time for a while, which is all written down in the runbook, somewhere, which brings us back to the question of how the service actually works.
